- RequestPublication paso a persistir status tipado (no String) y default PENDING en creacion.

Reglas de negocio cubiertas:
- Solo se aceptan estados validos del flujo definido.
- Toda solicitud nueva inicia en estado PENDING.
- Se evita manipulacion de estado desde payload de creacion.

Decisiones importantes:
- Estado de request representado como enum (tipado fuerte) para evitar valores invalidos.
- Contrato de error uniforme para facilitar consumo desde frontend y testing.

Que se implemento:
- Se agrego `POST /api/publications/{publicationId}/requests`.
- Se agrego `GET /api/publications/{publicationId}/requests`.
- Se agrego `PATCH /api/request-publications/{id}/cancel`.
- Se agrego `PATCH /api/request-publications/{id}/reject`.
- Se incorporaron validaciones de flujo y transiciones de estado en el servicio.

Reglas de negocio cubiertas:
- El requester no puede crear solicitud sobre su propia publicacion.

- Solo solicitudes `PENDING` pueden cancelarse o rechazarse.

- Se elimino la restriccion unica DB `(publication_id, requester_id)` para permitir historico y controlar duplicado activo por regla de negocio.
- Las validaciones del flujo se concentraron en `RequestPublicationService` para mantener consistencia entre endpoints.

- Aceptacion y Ride

- src/test/java/com/dbp/democarpultec/controller/RequestPublicationControllerTest.java
- src/test/java/com/dbp/democarpultec/service/RequestPublicationServiceTest.java

Que se implemento:
- Se agrego `PATCH /api/request-publications/{id}/accept` recibiendo `vehicleId`.
- El backend determina conductor/pasajero reales segun combinacion publication/request.
- Se valida que el vehiculo usado pertenezca al conductor real.
- Se crea Ride si no existe o se reutiliza para publicaciones de conductor.
- Se agrega RidePassenger en aceptaciones validas y se actualiza estado del request a `ACCEPTED`.

Reglas de negocio cubiertas:
- Solo el autor de la publicacion puede aceptar solicitudes.
- Solo requests `PENDING` pueden aceptarse.
- En publicacion de conductor se validan cupos disponibles antes de agregar pasajero.
- En publicacion de pasajero solo se acepta un conductor y se rechazan otros requests pendientes.

Decisiones importantes:
- La aceptacion se hizo transaccional para mantener consistencia entre request, ride y ride_passenger.
- Se centralizo el flujo de aceptacion en `RequestPublicationService` para evitar logica dispersa.
